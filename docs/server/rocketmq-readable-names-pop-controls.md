# POP 排空指标的隔离正反控制

本项属于 T11 准备，**尚未通过真实验证，不是生产排空或切换许可**。它使用原公开SDK隔离矩阵的真实Go/Python订阅、三物理输入和共享两槽预算；不新增业务操作，不改变SDK、宿主、Broker或生产worker。

原共享预算测试增加可选观察阶段，默认`None`保持原行为及计数。可读路由矩阵的public两档显式启用`--sdk-pop-drain-controls`，在原31项之外增加4项；live-recovery仍独立5项，M3/M4默认门禁保持。

1. 在独立新建CI项目核对POP buffer与未来revive timer基线，缺少buffer或格式冲突直接失败。新项目尚无计时记录时，基线允许timer序列尚未出现，并在报告明确记录；它不适用于生产排空。
2. 消费者真实就绪后、任何本轮共享消息发布前，核对其原生登记为ACTIVELY。此查询放在消息持有前，避免占用15秒不可见窗口。
3. 真实两条delivery保持在原handler内、不释放ACK；必须看到未来revive timer计数大于0。普通group在途gauge不能覆盖这个阳性责任。
4. 按原流程释放，核对全部9条原ID/wire被ACK并完整关闭客户端；再要求显式timer序列及两个buffer均为0，并复读。timer序列此后缺失不能记为0。

只读观察器只在GitHub-hosted Linux、原隔离项目标签及回环指标端口运行；不修改全局客户端factory、不跨线程共享session、不确认delivery、不改变MQ/DB状态。构造函数不读网络或启动任务。基线与结果仅输出计数和摘要，原fixture继续持有并清理真实子进程、连接与数据。

本地仅完成解析/缺失/重复/溢出/未来责任及观察顺序保护测试，真实控制仍由CI执行。该控制证明指标能阻止“持有消息却误判空”的错误，最终生产仍须封写、原生队列/重试/事务/业务回执完整证据及最新快照。[唯一执行总表](rocketmq-readable-names-execution.md)。
