# 可读命名验证的 CI 派发规则

本批[进度总表](rocketmq-readable-names-execution.md)的最终验收矩阵保持不变。调整的是触发范围和派发次数，不把取消、未选中的任务或纯契约测试当作原生验收通过。

- Replan 与未来调度 PR 只自动运行契约验证；两档真实 MySQL/Broker 验证只从 `workflow_dispatch` 进入。每个冻结源码候选仅派发一次完整矩阵，先查询是否已有同候选运行；已有运行就跟踪原运行，不追加相同手动运行，不设置失败自动重跑。
- 六个通用 SDK/Broker 工作流不再因明确属于 Replan、切换演练或发布器的隔离夹具单独变动而自动启动重型矩阵。这些具名文件由其专属契约/原生门禁验证；新增全局纯契约工作流覆盖所有 MQ 测试。
- 共用 `ci-transactions.py`、`qs_evaluation_acceptance.py`、Broker/Compose 配置及未知共享脚本仍触发原矩阵。工作流自身变化仍验证自身；手动完整矩阵入口、版本、矩阵及通过计数均保留。
- 当前 PR 若同时包含共用脚本与隔离夹具修改，仍执行原共用脚本回归。负向匹配不能借助夹具路径隐藏其他共用文件的变化。
- main 合并后的纯契约由统一工作流执行，取消同一改动在 PR 验证后再次自动启动通用 Broker Docker 重型验证。相关 PR 原生回归与最终合并候选的手动完整矩阵仍是发布门禁，不以 main 纯契约替代。

原生失败必须保留失败记录、精确源码和清理结果。后续派发须对应已定位的修复或一次具名诊断变更，禁止无变更地循环重跑直到绿色。

首次 Replan 专项的两个 MySQL 档均保留为失败：原宿主 9 项通过，新增历史确认断言有误。宿主 `Confirm` 只查询当前活动执行，Replan 已将活动引用移到新 fence；历史 Aborted 应由旧 Reference 的精确 witness/Checker 证明。修复夹具不改变 SDK 或业务确认接口，额外保留阶段、断言行号和固定错误分类，不上传原始错误、正文、wire 或凭据。修复的原生结果仍须独立记录，代码修复本身不表示通过。
