# 可读命名：八实例兼容切换演练

本演练对应 [执行总表](rocketmq-readable-names-execution.md) T11 的运行与恢复子门禁；提供演练入口不表示已经通过。

使用同一份冻结的五个候选镜像，先运行兼容 v2 哈希配置，再切换 v3 可读配置。八个实例的内存、CPU、Unix 身份、三个 worker 的并发 48、四个数据库绑定及 writer epoch 保持不变。宿主发布准入始终关闭，Checker 继续运行；无生产连接、业务调用、数据库恢复或模型调用。

入口为 `.github/workflows/rocketmq-readable-cutover.yml`，仅 GitHub-hosted Ubuntu runner 可实际执行。传入已提交的 `candidate_path` 和独立成功的 `startup_run_id`。先核验该启动运行的工作流、事件、源码 SHA、原始报告及同一候选，再验证原构建的五份 archive 和元数据，之后才建立隔离依赖。MacBook 不启动 Docker 依赖。

演练复用原生产配置打包器和 API 原生 freeze/preflight：原 21 个合成材料文件保留，另建兼容与活动两套不可变版本。只有八实例全部正常退出后才能改变材料 selector；API 使用实际宿主工具冻结并重复验证。四个精确数据库绑定及协议零记录快照在切换前后保持一致。20 个旧新 Topic 都必须为空，不复制 offset。

验证实际兼容配置启动，维护计时后停止旧实例，切换活动配置并在首次启动之前实际恢复兼容配置。配置切换与恢复通过协调器的离线维护入口执行；数据库恢复入口会永久封闭普通启动，保留其原有保护语义。随后由持久化协调器先记录首次启动边界，再启动 IAM；给 AI 指定经核对不存在的隔离网络，观察真实 Docker 启动失败。此后拒绝旧配置恢复及普通重试，仅允许同一候选的具名前向修复。八实例重新就绪后结束维护计时，上限 1800 秒，另记是否满足 900 秒目标。

完整报告须包含原启动 18 项及切换 7 项，共 25 项，零失败、零跳过，八实例最终正常退出、无运行时 DDL、所有隔离依赖和材料根目录清理完毕。缺少独立启动 receipt、候选不符、资源扩大或首次启动后试图恢复旧配置都不能通过。

本演练证明范围限于**同一兼容候选镜像、空输入、实际配置与容器切换**。不证明原生产旧镜像、不证明非空调度交接或 system 业务链路；这些仍由历史/未来调度、宿主业务故障及最终生产验收分别提供证据。本报告不能单独勾选整个 T11，须结合宿主业务、成对真实故障和 POP 责任检查；不得据此勾选 T14/T15。
